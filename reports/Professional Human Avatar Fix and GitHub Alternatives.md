# Professional Human Avatar: Fix Assessment and GitHub Alternatives

**Scope of this report:** the female AI-interviewer avatar built this session
on the FLAME/Humanoid-Face-3D photo-reconstruction pipeline. Investigation
first, then real GitHub research into replacing the problematic parts
(hair + upper body), then a technical decision, per the task's required
process. The male avatar was not touched. No branch switches, resets,
stashes, commits, or deletions were performed; all changes described below
are additive edits to files already created this session.

---

## 1. Current implementation architecture

**Pipeline, end to end:**

1. **Face geometry + texture**: `NetPranav/Humanoid-Face-3D`
   (`experiments/photo-avatar-conversion-v2/Humanoid-Face-3D/`), a FLAME-2023-Open-based
   single-photo fitter. Produces a 5023-vertex mesh with a baked
   `head_albedo_diffuse.png` texture (sharpened this session with an unsharp
   mask) and 52 ARKit blendshape deltas (`blendshapes_arkit52.json`).
2. **Hair + body**: **not part of that pipeline at all** — FLAME only
   models skull geometry. 100% procedural code written this session in
   `experiments/photo-avatar-conversion-v2/Humanoid-Face-3D/scripts/build_full_avatar.py`
   (928 lines):
   - `build_hair_shell()` (line 368) — a parametric dome mesh, flat/vertex-colored, no texture.
   - `build_hair_cards()` (line 513) — curved ribbon strips with an alpha-cutout strand texture, layered at the sides/back.
   - `build_torso()` (line 217) + `build_arm_and_hand()` (line 255) — tube-lofted cylinders (`tube_along_path()`, line 117) for the torso, arms, palms, and fingers, flat vertex-colored, **no UV texture anywhere on the body**.
3. **Assembly**: all of the above are merged into one GLB with 4 glTF
   primitives sharing one mesh/node (face-textured, body-vertex-colored,
   hair-cards-alpha-textured, hair-shell-vertex-colored).
4. **Rendering**: a custom Three.js page,
   `experiments/conversation-avatar-poc/nextjs-poc/app/photo-avatar-verify/page.tsx`
   — `GLTFLoader` (line 24), 3-point + hemisphere lighting (lines 90-105),
   `ACESFilmicToneMapping` (line 107). ARKit names are read directly from
   the raw GLB bytes (`parseArkitNames()`, line 156) because this exporter's
   morph-target naming at the mesh level is wrong — a detail already
   diagnosed and worked around earlier this session.
5. **Voice/animation pipeline** (unchanged, confirmed working, see §10):
   Kokoro TTS + wav2arkit ONNX inference served by
   `experiments/conversation-avatar-poc/service/persistent_service.py` on
   port 8912 (`/synthesize` endpoint), faster-whisper STT, Ollama LLM. This
   report does not touch any of it.

### Answering the required investigation questions directly

1. **Face geometry model**: FLAME 2023 Open (CC-BY-4.0), fitted per-subject by Humanoid-Face-3D's Phase-1 fitter.
2. **Head/scalp model**: there is no separate head/scalp model — FLAME's own skull mesh *is* the head/scalp geometry; hair is bolted on afterward by this session's own code, not generated by any model.
3. **Face texture application**: a single baked 2048x2048 photo-projection texture, UV-mapped onto the FLAME mesh, applied as a standard glTF `baseColorTexture`.
4. **Is hair a separate mesh?** Yes — two separate glTF primitives (shell + cards), entirely disjoint from the face primitive, sharing only approximate spatial adjacency, not actual mesh connectivity.
5. **Why the hairline boundary**: confirmed by direct inspection of `report.json` — only **33%** of the face texture is *observed* from the real photo; **64%** is generic *synthesized own-skin fill* for the scalp/sides/back the single photo never saw. So the hairline is two different rendering techniques (a flat procedural shell vs. a mostly-synthetic, texture-less-feeling photo fill) meeting at an edge, with every attempt to blend that edge limited by there being no real photographic hair detail underneath to blend into.
6. **Overlaps/gaps/normals**: checked directly, not assumed — a genuine shoulder geometry defect (sharp conical spike from an under-smoothed ring-scale profile) and a related "fin" artifact (a capped tube-end disc misaligned with the torso surface) were found and fixed this session (§8). No other mesh intersections or z-fighting were found in this pass.
7. **Different materials for face/ears/neck/body?**: yes, confirmed — face is one textured material; body (including where it visually should read as neck-colored skin) is a second, flat vertex-colored material with no texture at all. This is the direct, confirmed cause of the "low-poly mannequin" body complaint.
8. **Body/hands/clothing generation**: pure parametric geometry (circular/oval tube lofts) authored in Python this session, no scan, no sculpt, no cloth sim.
9. **Rendering library/formats**: Three.js + glTF/GLB (binary glTF 2.0), standard `GLTFLoader`, no custom shaders.
10. **Can the current model reach seamless photorealism without replacing its geometry?** No — see §3.

## 2. Root causes of every visible problem (mapped to evidence, not assumption)

| Symptom | Root cause | Evidence |
|---|---|---|
| Hair looks like a separate cap | Flat procedural shell meeting a mostly-synthesized (non-photographic) texture region, with an originally-unblended color edge | `report.json` texture_fractions (33% observed / 64% synthesized); fixed partially with color feathering, see §8 |
| Hair sides/back look artificial | Ribbon "cards" are literally flat quads; a flat ribbon viewed edge-on degenerates to a thin line or jagged spike | Diagnosed and fixed this session via cross-quad (two perpendicular ribbons per strand) |
| Shoulders/arms "basic geometric shapes" | Torso ring-scale profile had a sharp overshoot-then-retract (`1.55→1.95→1.75` over 2 steps, no smoothing) — a textbook conical-spike artifact on a radial loft | Fixed this session (9 rings instead of 6); confirmed in before/after screenshots |
| Hands "unnatural" | Simple tube-lofted cylinders for fingers/palm, no sculpted knuckle/joint detail | Structural — tube lofts cannot produce true hand anatomy without a sculpting tool |
| Neck-to-shoulder transition | A capped tube-end disc (added to fix an earlier dark-gap defect) sat at a mismatched angle vs. the torso surface, reading as a separate "fin" | Root-caused and fixed this session (removed a bad embed offset) |
| Clothing "flat, no fabric detail" | Body material has **zero texture/normal map infrastructure** — confirmed directly in the material definition, not inferred from appearance | Partially addressed this session with a procedural normal-perturbation "weave" shading effect (material-only, no new geometry risk) |
| Hair reads as a shinier, separate "plastic" piece | **Not actually a specular/roughness problem** — verified by direct pixel sampling that two large roughness changes (0.45→0.68→0.86) produced zero measurable change in the rendered highlight. The real cause: a perfectly smooth dome under one directional light shows an unbroken Lambertian diffuse gradient regardless of roughness | Root-caused and partially fixed via added geometric surface irregularity + multi-scale color noise, confirmed visually at a matched crop (see `avatar_visual_quality_assets/crown_before_round2.png` vs. `crown_after_round2.png`) |

**Pattern across this entire session's iteration history:** helmet-look →
spiky cards → jagged silhouette → shoulder spike → shoulder "fin" → hair
shininess. Each fix surfaced a new, different symptom in the same
hair/body subsystem. That pattern — not any single screenshot — is the
strongest evidence that the *procedural-geometry approach itself*, not any
one parameter, is the limiting factor.

## 3. Is the current avatar technically fixable?

**Split verdict, by component:**

- **Face: yes, already fixed/good.** Real photo texture, correct topology,
  52 working ARKit blendshapes, confirmed lip-sync. No further geometry
  work needed here.
- **Hair and body (procedural, hand-scripted): fixable to "better," not to
  "seamless photoreal."** Every fix this session was real and verified
  (not cosmetic slider-tuning — each came with a measured root cause), and
  each one worked. But the *category* of problem (sharp silhouette edges
  from simple parametric primitives; flat materials with no texture
  pipeline; smooth Lambertian gradients reading as plastic) recurs because
  the underlying technique — scripted tube lofts and parametric domes with
  flat vertex color — is not the technique real sculpted/scanned
  characters use. A genuinely seamless result needs either a sculpting tool
  (Blender, ZBrush) to author real hair/cloth geometry and UV-textured
  materials, or a fundamentally different acquisition method (full-body
  scan, multi-view capture) — neither is available in this environment.

## 4. GitHub repositories investigated

Research was delegated to an independent research pass (web search +
direct repo/license verification), explicitly separating README claims
from verifiable repo facts, per the task's requirement. Full candidate
list and verdicts:

### 2D audio-driven talking-head candidates (an alternative category raised explicitly in the task, since 2D sidesteps "reconstructing unseen 3D geometry" entirely)

| Candidate | Verdict | Disqualifying/qualifying fact |
|---|---|---|
| **MuseTalk** ([TMElyralab/MuseTalk](https://github.com/TMElyralab/MuseTalk)) | **Disqualified — hardware** | License is genuinely clean (code MIT, weights usable commercially, verified). But it is GPU-only; the repo's own minimum tested GPU is an RTX 3050 Ti (4GB VRAM); no CPU path exists. This machine has no NVIDIA GPU. |
| **Wav2Lip** ([Rudrabha/Wav2Lip](https://github.com/Rudrabha/Wav2Lip)) | **Disqualified — license** | Repo states directly: "can only be used for personal/research/non-commercial purposes... any form of commercial use is strictly prohibited." |
| **SadTalker** ([OpenTalker/SadTalker](https://github.com/OpenTalker/SadTalker)) | **Disqualified — license + architecture** | Apache-2.0 header, but bundles Wav2Lip's own non-commercial-only weights for mouth rendering — the restriction carries through regardless of SadTalker's own license text. Also an offline batch video renderer (seconds-to-minutes per clip), not compatible with this system's live, sentence-streamed, barge-in-interruptible loop. |
| **LivePortrait** ([KwaiVGI/LivePortrait](https://github.com/KwaiVGI/LivePortrait)) | **Disqualified — license + wrong modality** | Own code MIT, but depends on InsightFace's `buffalo_l` models, which are non-commercial — the same "poisoned by a dependency" problem. Core mode is video-driven reenactment, not audio-driven lip-sync. |
| **EchoMimic / EchoMimicV2** | **Disqualified — hardware** | Diffusion-based, requires CUDA 11.7+; not practically CPU-runnable; offline-batch, not live. |
| **Hallo** ([fudan-generative-vision/hallo](https://github.com/fudan-generative-vision/hallo)) | **Disqualified — hardware** | Code LICENSE confirmed MIT (genuinely clean), but diffusion-based, GPU/VRAM-heavy, no CPU benchmarks, offline-batch. |
| **AniPortrait** | **Unresearched, not cleared** | License text not independently verified; same diffusion/GPU/offline-batch category as the above regardless. |

### 3D full-head+hair+body candidates (beyond LAM and NetPranav/Humanoid-Face-3D, both already evaluated and in-use/rejected earlier this session)

| Candidate | Verdict | Fact |
|---|---|---|
| SOAP | Disqualified — license | "publicly available for research purposes" (non-commercial) |
| DiffLocks (MPI, single-image 3D hair) | Disqualified — license | Academic-only; commercial path exists only as a *paid* third-party license (Meshcapade) |
| FaceLift (Adobe) | Disqualified — license + output type | Code Apache-2.0, but model weights under Adobe's non-commercial Research License; also outputs an unriggable 3D Gaussian head, not a mesh |
| PERSE | Disqualified — unavailable | No published code found |

**No credible, currently-maintained, commercially-licensed, CPU/modest-hardware-feasible open-source alternative was found for either category.** This is a consistent pattern, not a gap in the search: essentially every actively-developed project in this space is released non-commercially, or has at least one bundled dependency (InsightFace, MICA-derived assets, proprietary research weights) that poisons an otherwise-permissive top-level license.

## 7. Recommended solution and reasons

**Path A: keep and continue improving the current implementation.**

This is not a default or a shortcut — it is the only option that satisfies
every hard constraint simultaneously (CPU-only, no Blender, commercial
license, browser-renderable, ARKit-52/lip-sync-compatible, live and
barge-in-capable). Every researched alternative fails at least one of
these, usually two. Per the task's own instruction — "if no existing
solution meets the requirements and licensing constraints, clearly say
so" — that is the honest conclusion here, not a forced integration.

This does **not** mean the current avatar is as good as it can look. It
means further improvement has to come from either (a) continued procedural
polishing within the current architecture (already yielding real, if
incremental, gains this session — see §8), or (b) acquiring a sculpting/UV
tool (Blender is free and could in principle be installed later — that was
out of scope for this environment this session, but is the actual correct
long-term fix for "looks like separate parts," not a code change).

## 8. Changes implemented this session (cumulative, including prior rounds)

All in `experiments/photo-avatar-conversion-v2/Humanoid-Face-3D/scripts/build_full_avatar.py`.
No changes to the face primitive, its UVs, its texture, its 52 ARKit
targets, the MediaPipe/viseme pipeline, the rendering page's camera, or the
male avatar.

1. Hair: replaced an earlier "helmet" dome with a tight scalp shell + flow
   cards; fixed a face-obscuring card bug; fixed card-density/jagged-edge
   aliasing; fixed a flat-ribbon-viewed-edge-on artifact via cross-quad
   cards.
2. Shoulder: smoothed the torso ring-scale profile (9 rings, no sharp
   overshoot) — spike eliminated.
3. Shoulder "fin": removed a mismatched embed offset on the arm's capped
   starting disc.
4. Clothing: added procedural fabric-weave normal perturbation (shading
   only, no geometry/UV changes).
5. Hairline: added color feathering at the shell boundary (narrowed and
   made non-linear after an initial attempt produced a visible orange
   halo — caught and corrected before shipping).
6. Hair "plastic" look: root-caused to diffuse-gradient smoothness (not
   roughness, confirmed by measurement); added interior-only geometric
   surface irregularity and multi-scale color noise.

No new changes were made in **this** report's pass beyond what is already
documented above — per instruction, cosmetic iteration was not continued
without a newly identified, reproducible issue. This report instead
focused on the investigation and alternatives-research it was asked for.

## 12. Hardware requirements and benchmarks

- **Current implementation**: confirmed CPU-only throughout this entire
  session (reconstruction, TTS, STT, LLM, rendering) — no GPU benchmark
  needed because none is used.
- **Alternatives researched**: no benchmark was run for any of them, since
  every candidate was disqualified on license and/or a documented hardware
  requirement (GPU/CUDA) before reaching the point of local testing being
  worthwhile. Where a repo cites its own tested minimum GPU (e.g.,
  MuseTalk's RTX 3050 Ti), that figure is reported as-is from the source,
  not independently re-benchmarked.

## 13. Remaining limitations (stated plainly)

- Hair and body remain procedurally generated, not sculpted; they read as
  "good for interview-camera framing," not "indistinguishable from a real
  photo" under close scrutiny. This is now confirmed to be the practical
  ceiling of the available toolchain, not a tuning gap — both by this
  session's own iteration history and by the absence of any qualifying
  open-source replacement.
- The hairline transition is improved but not fully seamless (see
  `Avatar Visual Quality Improvement.md` for the specific attempted fixes
  and why a fully seamless result would require either real-time alpha
  compositing into the face texture or new hair-texture content neither of
  which was safe to attempt without further validation this session).
- Eye-blink animation is flat at the data source (viseme model), separate
  from everything else in this report.
- No path exists today, under this project's real constraints (no paid
  APIs, no GPU, commercial license required), to a fundamentally more
  realistic open-source avatar pipeline than the one already in place. If
  that changes (e.g., a GPU becomes available, or Blender/sculpting time is
  budgeted), MuseTalk (2D, if GPU becomes available) and manual
  Blender-authored hair/cloth (3D, if sculpting time becomes available) are
  the two concrete, evidence-backed paths worth revisiting first.
