# No single open-source repo closes this gap

No genuinely open-source, self-hostable repository takes a single photograph and produces a realistic, animatable GLB with ARKit or Oculus-named blendshapes ready to drop into `setAvatar(url, morphTargets)` — every real candidate found stops at a static OBJ/PLY mesh, a FLAME/3DMM parameter set, or a Gaussian splat, and **every path to a rigged, blendshape-driven GLB requires building custom conversion and rigging tooling that does not exist today as a maintained package** ([ujjawalcse/3D-Virtual-Avatar](https://github.com/ujjawalcse/3D-Virtual-Avatar) is the only project that even attempts the full chain, and it is a 1-star personal proof-of-concept stitching together six-plus upstream tools). Worse, the licensing picture is a trap: the most capable reconstruction family (DECA/EMOCA/MICA, built on the FLAME head model) ships MIT-*looking* repositories whose actual LICENSE files are Max-Planck-Institute "non-commercial scientific research purposes" grants, and the FLAME model those repos depend on carries the same restriction for every version these tools were trained against ([DECA LICENSE](https://raw.githubusercontent.com/yfeng95/DECA/master/LICENSE), [FLAME model license](https://flame.is.tue.mpg.de/modellicense.html)). The more commercially-clean candidates (3DDFA_V2, HRN, SynergyNet — genuinely MIT/Apache-2.0 at the code level) buy that permissiveness by producing lower-detail, non-FLAME-topology meshes with no existing blendshape ecosystem and, for at least one, an unverified base-model dependency that could reintroduce the same restriction. Gaussian-splatting single-image methods (GAGAvatar) deliver the most photorealistic *rendering* but produce no mesh at all — not a conversion problem but a fundamentally different, unsolved geometry representation that cannot be loaded as a Three.js `SkinnedMesh`. The practically honest conclusion: the top-ranked approach for this SDK is DECA/EMOCA plus a from-scratch FLAME-topology blendshape rig and deformation-transfer bridge, but it is blocked for commercial deployment unless a separate commercial license is negotiated with the Max Planck Institute, or the pipeline is rebuilt on an MIT-licensed, non-FLAME reconstruction model with a bespoke blendshape rig built from zero.

## The licensing pattern repeats across every capable candidate

Every FLAME-based face reconstruction model surveyed — DECA, EMOCA, and MICA — carries a nearly identical LICENSE file: "Software Copyright License for non-commercial scientific research purposes," which explicitly states "any other use, in particular any use for commercial, pornographic, military, or surveillance purposes is prohibited," with commercial licensing requiring direct contact with `ps-license@tue.mpg.de` ([DECA LICENSE](https://raw.githubusercontent.com/yfeng95/DECA/master/LICENSE), [EMOCA LICENSE](https://raw.githubusercontent.com/radekd91/emoca/master/LICENSE), [MICA LICENSE](https://raw.githubusercontent.com/Zielon/MICA/master/LICENSE)). This is not an incidental restriction the maintainers forgot to loosen — the research notes infer it traces back to the underlying face-scan and texture-space training data (e.g., the Basel Face Model-derived albedo space) that the academic authors do not themselves have the right to relicense permissively. Compounding this, the FLAME parametric head model that DECA/EMOCA/MICA all depend on is itself non-commercial for every version except a newer "FLAME 2023 Open" release under CC-BY-4.0 — but none of the reviewed pretrained pipelines were confirmed to have been retrained or verified compatible with that permissive variant, so the safe assumption is that the original non-commercial FLAME terms still govern the pretrained weights actually in use ([FLAME homepage](https://flame.is.tue.mpg.de/), [FLAME-Universe](https://github.com/TimoBolkart/FLAME-Universe)). ROME (SamsungLabs), the one academic repo explicitly framed as "photo → rigged, renderable head avatar," inherits this same restriction because it requires DECA and FLAME as mandatory dependencies, and even then its "rig" is a neural rendering network rather than a glTF skeletal or morph-target rig — it has never been shown to produce anything GLB-importable ([SamsungLabs/rome](https://github.com/SamsungLabs/rome)). By contrast, the repos that are genuinely clean at the code level — **3DDFA_V2** (MIT, confirmed via direct LICENSE fetch, CPU-capable), **Deep3DFaceRecon_pytorch** (MIT code, but a *mandatory* Basel Face Model 2009 dependency whose own license terms were never retrieved in this research and remain an open question), **HRN** (Apache-2.0 per GitHub's license detection, but its underlying parametric base model's license was never named in the README and is an unresolved gap), and **SynergyNet** (MIT, no separately-licensed mandatory base model found) — buy that permissiveness at the cost of lower reconstruction fidelity and a non-FLAME mesh topology with zero existing blendshape-conversion ecosystem built around it.

## No repo anywhere ships GLB export or ARKit/Oculus blendshapes natively

Across all three research tracks — classical mesh-based 3DMM/FLAME reconstruction, Gaussian-splatting/NeRF avatars, and end-to-end toolkit searches — **not one README documented a native GLB/glTF export path or ARKit/Oculus-named blendshape output**. DECA, 3DDFA_V2, MICA, Deep3DFaceRecon_pytorch, EMOCA, HRN, and SynergyNet all stop at OBJ or PLY meshes with, at best, a UV texture map or baked vertex color. On the Gaussian-splatting side, GAGAvatar is a genuine one-shot, single-image method producing 3D Gaussians directly, but it exposes no mesh or GLB export at all — expression is driven through FLAME-derived `expcode`/`posecode` parameters from a separate tracker, not morph targets, and converting its splat output to a textured mesh would require an independent, nontrivial splat-to-surface reconstruction step the project does not provide ([GAGAvatar repo](https://github.com/xg-chu/GAGAvatar)). GaussianAvatars does bind Gaussians to a driving FLAME mesh — the strongest splat-to-blendshape bridge found in the entire survey — but it requires multi-view **video**, not a single photo, and is explicitly non-commercial under a dual CC-BY-NC-SA-4.0-plus-Toyota-Motor-Europe clause, disqualifying it outright on both the input-type and licensing axes ([GaussianAvatars repo](https://github.com/ShenhanQian/GaussianAvatars)). General-object splat-to-mesh tools like LGM do ship an official Gaussian-to-mesh conversion script via nvdiffrast, the clearest "official" conversion path found anywhere in this research, but LGM has zero head/face specialization (trained only on Objaverse synthetic objects) and no facial-expression mechanism whatsoever, making it unsuitable for a talking-avatar pipeline regardless of its technical maturity ([LGM repo](https://github.com/3DTopia/LGM)). Critically, no open-source project was found that maps **FLAME's own expression-parameter space onto the 52 named ARKit blendshapes** — FLAME's expression basis is a PCA/corrective-blendshape space derived from training data, structurally different from ARKit's hand-authored, semantically named shapes, so no simple relabeling is possible; the only semi-relevant published work (a 2024 Eurographics poster mapping OpenFace Action Units to ARKit weights) never released accompanying code. The one project that explicitly tries to assemble a full photo-to-rigged-GLB chain, ujjawalcse/3D-Virtual-Avatar, routes through DECA/PIXIE → SPECTRE/EMOCA → NVIDIA Omniverse Audio2Face → Neural Blend Shapes → Blender `bpy` export, a stack of six-plus heterogeneous research and proprietary-adjacent components with 1 GitHub star and no confirmed maintenance — direct evidence that fragmentation, not a packaged solution, is the actual state of this field ([ujjawalcse/3D-Virtual-Avatar](https://github.com/ujjawalcse/3D-Virtual-Avatar)).

## Ranking the top three approaches for this SDK

Weighing realistic appearance, single-photo support, bridge potential to ARKit/Oculus blendshapes, expression/blink coverage, GLB+Three.js compatibility, and fully local execution, three approaches separate from the rest — though all three require substantial custom engineering and none is commercially unblocked without further work.

| Rank | Approach | Realism | Single photo | Blendshape bridge | Blink/expression | GLB+Three.js | Local execution | Licensing status |
|---|---|---|---|---|---|---|---|---|
| 1 | **DECA/EMOCA (FLAME-based)** | High — purpose-built for detailed, animatable face capture | Yes, confirmed | FLAME topology is the most-documented, most-reusable bridge target despite no existing converter | FLAME's pose parameters cover jaw/eyelid pose; full named blink/ARKit shapes still need manual authoring | Requires full custom conversion (OBJ+texture → rigged GLB) | Yes, PyTorch + optional PyTorch3D, no extreme VRAM figures documented | **Non-commercial only** — code and FLAME weights both restricted ([DECA LICENSE](https://raw.githubusercontent.com/yfeng95/DECA/master/LICENSE), [FLAME license](https://flame.is.tue.mpg.de/modellicense.html)) |
| 2 | **3DDFA_V2 (MIT, dense alignment)** | Moderate — dense mesh + UV texture, less detailed than DECA/EMOCA | Yes, confirmed; CPU-only, ~1.35ms/image | Non-FLAME (BFM/3DMM) topology — no existing blendshape ecosystem built around it | No documented expression/blink output beyond pose | Requires full custom conversion; no documented export tooling at all | Yes, genuinely CPU-only ([README](https://raw.githubusercontent.com/cleardusk/3DDFA_V2/master/readme.md)) | **MIT**, commercially permissive at the code level; detector sub-component license unverified |
| 3 | **Gaussian-splat single-image (GAGAvatar)** | Highest potential photorealism via novel-view rendering | Yes, genuine one-shot feed-forward | Theoretical only, via FLAME-derived driving codes — no mesh exists to attach ARKit names to | Driven by FLAME-style codes from a separate tracker, not named blendshapes | **Fails** — no mesh/GLB export exists; splat-to-mesh is an unsolved research step, not a conversion script | Yes in principle, GPU required, VRAM unconfirmed | License label unclear (MIT claimed via GitHub sidebar, not confirmed full text); sub-asset (FLAME/EMICA/VGGHead) licenses unverified |

DECA/EMOCA ranks first specifically because FLAME's fixed, well-documented topology is the only mesh representation in this entire survey with any plausible reusable path to a blendshape rig — the rigging research explicitly concludes FLAME topology is "the most promising long-term path for ARKit conversion" even while confirming no such converter currently exists. It loses points only on licensing, which is a hard, not soft, blocker: commercial use requires a negotiated license from the Max Planck Institute. 3DDFA_V2 ranks second as the pragmatic, fully-commercial-clean fallback, trading reconstruction fidelity and ecosystem tooling for legal safety and CPU-only local execution. Gaussian splatting via GAGAvatar ranks third on pure visual-quality potential but is disqualified from near-term integration by the complete absence of a mesh — this SDK's renderer loads GLB `SkinnedMesh` geometry with named morph targets, and a point cloud of Gaussians is not reducible to that without inventing new surface-reconstruction research, not just a script. A fourth-place honorable mention is Microsoft's GASP, which on paper promises exactly single-photo Gaussian avatar enrollment, but as of this research no public code repository exists for it at all, so it cannot be evaluated or adopted today ([GASP project page](https://microsoft.github.io/GASP)).

## The complete DECA/EMOCA pipeline, stage by stage, including every missing piece

Because no existing repo performs this chain, the practical build-out for the top-ranked approach looks like this, with every gap and licensing blocker called out explicitly rather than assumed solvable.

**Stage 1 — Single photo → 3D reconstruction.** Run DECA or EMOCA inference on one in-the-wild photo to get a FLAME-topology mesh with optional extracted texture ([DECA README](https://raw.githubusercontent.com/yfeng95/DECA/master/README.md)). **Licensing blocker:** both the DECA/EMOCA code license and the FLAME model license are "non-commercial scientific research purposes" only; any commercial deployment of this stage requires contacting `ps-license@tue.mpg.de` for DECA/EMOCA and separately the FLAME licensing contact, since the pretrained weights were built against FLAME's original non-commercial releases, not the newer CC-BY-4.0 "FLAME 2023 Open" variant ([FLAME license](https://flame.is.tue.mpg.de/modellicense.html)). EMOCA's own README additionally flags the project as deprecated in favor of a successor library ("inferno") whose licensing was not evaluated in this research and would need separate verification before being substituted in.

**Stage 2 — Facial rig and blendshapes: the single biggest missing piece.** No FLAME-to-ARKit (or FLAME-to-Oculus-viseme) converter exists anywhere in the open-source ecosystem searched. The only viable path requires building two things that currently do not exist as packaged tools: (a) a **one-time manual template rig** — build or acquire a single FLAME-topology head, rig it with bones/drivers, and hand-pose it through all 52 ARKit reference expressions plus a separate set of 15 Oculus viseme shapes (the latter is an extra, uncovered gap — the Blender add-ons found, `elijah-atkins/ARKitBlendshapeHelper` and `tsikerdekis/ARKit-Creator-Blender-Addon`, only automate baking the 52 ARKit shapes once a rig is already posable, and neither explicitly confirms its output shape-key name strings exactly match ARKit's camelCase convention — a manual QA pass is required either way) ([ARKitBlendshapeHelper](https://github.com/elijah-atkins/ARKitBlendshapeHelper), [ARKit-Creator-Blender-Addon](https://github.com/tsikerdekis/ARKit-Creator-Blender-Addon)); and (b) a **per-avatar automated transfer step** — since DECA/EMOCA output is already in FLAME topology, the template's 52+15 shape-key deltas should transfer by direct vertex correspondence, but where correspondence is imperfect (e.g., if sourcing a non-FLAME scan), non-rigid ICP (`wuhaozhe/pytorch-nicp`, GPU-accelerated, BFM-template-oriented) establishes registration and a deformation-transfer tool (`jerenchen/deformxfer`, BSD-3-Clause, explicitly derived from a facial-blendshape-avatar paper, or `mickare/Deformation-Transfer-for-Triangle-Meshes`, MIT, easier to debug) carries the deltas onto the new personalized mesh. **This conversion script does not exist today and must be written from scratch**, gluing together at least three separate tools with their own format conversions and correspondence-quality QA.

**Stage 3 — GLB export.** A Blender `bpy` script must assemble the personalized FLAME mesh, its texture, and the 67 (52 ARKit + 15 Oculus) transferred shape keys, then export via Blender's native glTF2 exporter. Blender carries shape-key names through to the export as `mesh.extras.targetNames`, a Blender-exporter convention living in glTF's `extras` field rather than the core glTF 2.0 specification — the export script must ensure no shape key is muted (muted keys are silently dropped from the export, not zeroed) and, ideally, that the head mesh stays a single material/single primitive, since multi-material meshes get split into multiple glTF primitives and some viewers then show a duplicated morph-target slider set per primitive ([Three.js Discourse](https://discourse.threejs.org/t/animation-and-morph-target-gltf-export/14850), [Blender Artists thread](https://blenderartists.org/t/when-exporting-gltf-from-blender-multiple-meshes-appear-in-the-morph-target-in-the-viewer/1523555)).

**Stage 4 — Talking Avatar SDK integration.** This step is genuinely the easiest in the chain, because `@interviewflowai/talking-avatar`'s own `setAvatar(url, morphTargets)` API (confirmed directly in `src/TalkingAvatar.ts`) already accepts a custom `MorphTargetMap` — e.g. `{ viseme_PP: ["MouthClosed"], eyeBlinkLeft: "Blink_L" }` — that remaps the SDK's expected ARKit/Oculus names onto whatever shape-key names actually survive the Blender export. This meaningfully de-risks the naming-exactness concerns raised throughout Stage 2 and 3: the pipeline does not strictly need the Blender-exported names to be perfectly spelled ARKit strings, only consistently named so they can be mapped once. What remains unverified from the research notes is whether Three.js's `GLTFLoader` actually reads `extras.targetNames` into `mesh.morphTargetDictionary` automatically — this was flagged explicitly as an unconfirmed mechanism in the rigging notes and should be hands-on tested against the exact Three.js version this SDK uses before trusting the renderer to resolve morph targets by name at all.

**Stage 5 — Audio-driven lip-sync.** This stage is outside the scope of what the research notes covered — they focused on avatar *creation*, not the existing SDK's audio-to-viseme driving logic — so no new finding changes this stage; it should continue to work unmodified as long as Stage 2–4 deliver a GLB whose morph targets are correctly named or mapped via the existing `morphTargets` parameter.

## Conclusion

The research converges on an uncomfortable but clear verdict: the open-source photo-to-realistic-avatar space is bottlenecked not by a missing reconstruction model — DECA, EMOCA, 3DDFA_V2, and several Gaussian-splat methods all genuinely take a single photo and produce *something* 3D — but by the complete absence of any maintained bridge from those outputs to a named-blendshape glTF rig, combined with a licensing landscape where the highest-fidelity results are consistently non-commercial. The practical implication for this SDK is that no "integrate and ship" shortcut exists; the realistic path is to either accept the non-commercial DECA/EMOCA pipeline for internal/research use while separately pursuing a Max Planck commercial license, or invest the same from-scratch rigging and conversion engineering on top of the legally-cleaner but lower-fidelity 3DDFA_V2/HRN/SynergyNet family. Either way, the single highest-leverage artifact this project could build — and that currently does not exist anywhere in the open-source ecosystem searched — is a reusable FLAME-or-BFM-topology template head carrying all 52 ARKit shapes plus the 15 Oculus visemes, since every other step (reconstruction, non-rigid registration, deformation transfer, GLB export) already has at least one usable open-source tool, however unpolished, while the named-blendshape template itself does not.
