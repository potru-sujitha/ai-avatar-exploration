# Facial Rigging & Blendshape Generation — Open-Source Tools (FLAME/mesh → ARKit/Oculus morph targets for Three.js GLB)

## 1. FLAME-to-ARKit (or FLAME-to-blendshape) conversion — does a clean open-source converter exist?

### Takeaway
No clean, documented, open-source "FLAME-to-ARKit" converter exists. FLAME's expression space is a PCA/blendshape basis (50 expression coefficients + pose-dependent corrective blendshapes), and it is a *different* basis from the 52 named ARKit shapes — nothing in the FLAME ecosystem (flame-fitting, DECA, VHAP, photometric_optimization) ships an official or community mapping from FLAME coefficients to ARKit blendshape names. This has to be solved indirectly (deformation transfer or render-and-refit), not via an off-the-shelf script.

### Cited Findings
- FLAME's expression model is a linear PCA space ("additional global expression blendshapes") plus pose-dependent corrective blendshapes driven by jaw/eye/neck pose, not a named 52-shape ARKit basis — [VHAP repo description via search](https://github.com/ShenhanQian/VHAP)
- VHAP (ShenhanQian/VHAP), a FLAME-based head-tracking pipeline that fits FLAME to video and exports tracking results for Gaussian-avatar pipelines, requires downloading the FLAME 2023/2020 model assets separately and exposes a `flame_editor.py`/`flame_viewer.py` for inspecting FLAME's own vertex masks and expression basis — it does **not** expose or document any ARKit-named output; its internal `flame.py` model code is explicitly adapted from HavenFeng's `photometric_optimization/models/FLAME.py`, which carries its own restricted license — [Hugging Face vhap/model/flame.py mirror](https://huggingface.co/spaces/3DAIGC/LAM_h5/blob/main/vhap/model/flame.py)
- A Gitee mirror lists VHAP's license as CC-BY-NC-SA-4.0 (non-commercial, share-alike), while an ecosyste.ms listing shows "other" — the two sources disagree, so the exact license needs to be confirmed directly from the LICENSE file in the official `ShenhanQian/VHAP` repo before any commercial use is assumed — [Gitee mirror](https://gitee.com/hu-hanqing/VHAP); [ecosyste.ms listing](https://science.ecosyste.ms/projects/38857)
- Searches for an explicit "flame2arkit" or "FLAME to ARKit" repo turned up nothing; the only closely related published work found is a 2024 Eurographics poster that infers ARKit-compatible blendshape *weights* at runtime from OpenFace Action-Unit intensities via a GRU network (90% activation precision / 85% recall) — this maps Action Units → ARKit weights, not FLAME parameters → ARKit basis, and no code repository was found accompanying it — [Eurographics digital library item](https://diglib.eg.org/items/d8ceee83-6078-48dd-8290-3b15ae919abd/full)
- No "FLAME-Universe" repository or community page documenting an ARKit blendshape basis for FLAME was found in search results.

### Inferences
- The realistic path is NOT "run a converter script" — it is a two-stage manual/semi-automated workaround: (a) fit FLAME (or any FLAME-based reconstruction) to get a neutral head mesh in FLAME topology, then (b) use deformation transfer (see Section 2) to transfer a pre-built ARKit blendshape *set* from a template head (in FLAME topology or any topology) onto the fitted mesh, since FLAME's own expression parameters cannot be relabeled into ARKit names directly — this is because FLAME blendshapes and ARKit blendshapes are different, non-isomorphic bases (FLAME's are PCA components of a training corpus; ARKit's are hand-authored, semantically named sculpts).
- An alternative semi-automated workaround avoiding deformation transfer entirely: build one ARKit-rigged template head once (manually, in Blender, see Section 4) in a fixed topology, then for every new scanned/reconstructed head, non-rigidly fit (register) that template topology onto the new head's surface (effectively what FLAME fitting itself does, but with a custom ARKit-blendshape-bearing template instead of the stock FLAME template) so the new head inherits the ARKit shape keys "for free" because it now shares the template's topology and blend-shape deltas transfer by vertex ID. This reframes the problem as "fit my own ARKit-rigged template to new scans" rather than "convert FLAME output to ARKit" — which is the approach deformation-transfer and mesh-registration tools below are built for.

### Gaps
- No repository explicitly and verifiably maps FLAME expression-parameter space to the 52 ARKit blendshape names. If one exists, it is not discoverable via standard search as of November 2026.
- VHAP's exact license (CC-BY-NC-SA-4.0 vs "other") is unresolved from secondary sources — needs direct confirmation from `github.com/ShenhanQian/VHAP/blob/main/LICENSE` before any commercial decision.
- Whether the ARKit-mapping-from-Action-Units poster (Eurographics 2024) released code could not be confirmed.

## 2. Generic blendshape transfer / deformation transfer tools (Wrap3-style open alternatives)

### Takeaway
Multiple open-source implementations of Sumner & Popović's "Deformation Transfer for Triangle Meshes" exist and are genuinely usable as free Wrap3 alternatives for moving a blendshape set from a rigged template head onto a new unrigged scan, but none of them ship ARKit names out of the box — they transfer arbitrary shape deltas by correspondence, so the ARKit naming has to already exist on the source/template and is preserved only because the transfer tool is applied once per named shape.

### Cited Findings
- `kyle-gh/DeformationTransfer` — C++ implementation of the Sumner & Popović algorithm using CGAL and Eigen; ships two separate CLI tools: `corrtool` (for marking vertex correspondences between source and target) and `transfer` (applies the deformation once correspondence is set) — found via search, not independently license-confirmed — [GitHub](https://github.com/kyle-gh/DeformationTransfer)
- `jerenchen/deformxfer` — C++ implementation built on Eigen/libIGL, explicitly based on the "Landmark-guided Deformation Transfer of Template Facial Expressions for Automatic Generation of Avatar Blendshapes" paper (i.e., face-blendshape-specific, not generic). Reported as BSD-3-Clause licensed, with a demo program; README notes it was only tested on macOS — [GitHub](https://github.com/jerenchen/deformxfer)
- `mickare/Deformation-Transfer-for-Triangle-Meshes` — Python implementation with browser-based 3D visualization of each pipeline step. Confirmed via direct fetch: MIT License for the code; note that any bundled example/reference models in its `models/` folder carry their own third-party licenses, listed separately in that folder. It builds a correspondence mapping between a source and target mesh with *different vertex counts*, then transfers deformations using user-provided marker vertices; outputs include the correspondence map, transferred deformation, plots, and an HTML report. It is a generic triangle-mesh tool — the README does not mention faces or blendshapes specifically, so face-specific tuning (landmark placement, symmetric smile shapes, etc.) is on the user — [GitHub](https://github.com/mickare/Deformation-Transfer-for-Triangle-Meshes)
- `fabyday/deformation_transfer_for_window` — a Windows port of the original "Golevka" ANSI-C deformation-transfer implementation, built with CMake and SuiteSparse, including a correspondence tool — found via search only, license unconfirmed — [GitHub](https://github.com/fabyday/deformation_transfer_for_window)
- Non-rigid ICP (a prerequisite/alternative for building the vertex correspondence that deformation transfer needs) has several open implementations: `wuhaozhe/pytorch-nicp` is GPU-accelerated, explicitly designed for face registration using a BFM (Basel Face Model) template, supports both mesh-to-mesh and mesh-to-point-cloud registration, with separate configs for clean scans vs. noisy point clouds — [GitHub](https://github.com/wuhaozhe/pytorch-nicp)
- `saikiran321/nonrigid_icp` (a fork inspired by `charlienash/nricp`) implements "Optimal Step Nonrigid ICP Algorithms for Surface Registration" and is reported MIT-licensed — [GitHub](https://github.com/saikiran321/nonrigid_icp)
- `rafcy/nonrigid_icp` uses Open3D and scikit-sparse but its own TODO list states non-rigid registration is still unfinished — treat as a reference implementation only, not production-ready — [GitHub](https://github.com/rafcy/nonrigid_icp)
- For Blender specifically, `neongm/RinvosBlendshapeTransfer` ("Rinvo's Blendshape Transfer") is described as an automation wrapper around Blender's built-in Surface Deform modifier (not Shrinkwrap), supporting pre-processing (subdivision) and a paintable transfer mask; the author notes manual cleanup is often still required afterward — found via search, license not confirmed, and it is listed for sale on Booth.pm which suggests a possible paid/open hybrid distribution model that should be checked before relying on it as "free open source" — [GitHub](https://github.com/neongm/RinvosBlendshapeTransfer); [Booth listing](https://booth.pm/en/items/6437584)

### Inferences
- The most practical "bridge" pipeline with today's open-source tools is: (1) build or obtain one ARKit-named blendshape rig on a single template head topology (manual one-time effort, see Section 4); (2) run non-rigid ICP (e.g. `pytorch-nicp`, since it's already face/BFM-oriented and GPU-accelerated) to register the template onto each new scanned/reconstructed head, establishing per-vertex correspondence; (3) run deformation transfer (e.g. `deformxfer`, since it's explicitly derived from a facial-blendshape-avatar paper, or `mickare`'s Python tool for easier debugging) to push each of the 52 template blendshape deltas onto the new head using that correspondence. This is a per-avatar automatable pipeline once scripted, but requires real engineering investment to glue the three tools together (format conversions, correspondence-quality QA, symmetric-shape cleanup) — it is not a single off-the-shelf executable.
- None of these tools produce ARKit names "automatically" in the sense of inferring semantics — the names are only correct because they were already correct on the source/template and are carried through 1:1 by shape-key index/order during transfer. Any renaming mistake upstream (e.g., mislabeled template shapes) propagates silently.

### Gaps
- No confirmed maintenance/last-commit dates for `kyle-gh/DeformationTransfer`, `jerenchen/deformxfer`, `fabyday`'s port, or `RinvosBlendshapeTransfer` — fetched pages did not surface commit dates, only commit counts.
- `mickare/Deformation-Transfer-for-Triangle-Meshes`'s maintenance status (last commit date) also could not be confirmed, though its license (MIT) was directly confirmed.
- No head-to-head quality comparison between these tools for facial blendshape transfer specifically was found; `deformxfer` is the only one explicitly validated against a facial-avatar-blendshape paper.

## 3. MediaPipe Face Landmarker blendshapes as a driving signal (not mesh generation)

### Takeaway
MediaPipe's Face Landmarker Task outputs 52 blendshape coefficients whose names are explicitly in ARKit's naming convention (confirmed examples: `browDownLeft`, `browInnerUp`, `jawOpen`, `eyeBlinkRight`), and the MediaPipe code plus its model cards point to Apache 2.0 licensing — but this solves only the animation-signal problem (live facial-capture coefficients compatible by name with an ARKit-style rig), not mesh/rig creation; it still requires the GLB avatar to already have correctly-named morph targets for these coefficients to drive anything.

### Cited Findings
- Google's official Face Landmarker guide confirms the task outputs "52 facial expression coefficients" (direct quote-level fetch) and names at least four of them explicitly: `browDownLeft`, `browInnerUp`, `jawOpen`, `eyeBlinkRight` — matching ARKit's own naming convention — [Face landmark detection guide, developers.google.com](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker)
- That same official guide links three separate model cards for the underlying models used in the pipeline: a BlazeFace Short Range face-detection model card, a "MediaPipe Face Mesh V2" landmark model card, and a "Blendshape V2" model card for the blendshape-prediction model specifically — these are three distinct models chained together, each potentially with its own card/terms, rather than one monolithic license statement — [Face landmark detection guide](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker)
- Secondary sources (not Google's own primary license page) report Apache 2.0 for MediaPipe model weights: a Unity Sentis repackaging page states "All Google Mediapipe models are open source under the Apache 2.0 license" and that accompanying code "can be used commercially"; a Luxonis model listing for `mediapipe-face-landmarker` also lists Apache 2.0 with commercial use marked allowed — both are third-party, not Google's own authoritative statement — [Unity Sentis page](https://huggingface.co/unity/sentis-face-landmarks); [Luxonis model page](https://models.luxonis.com/luxonis/mediapipe-face-landmarker/aim_AHWHb5AGeTeUve3J2gk4Sy)
- A third-party ONNX repackaging of MediaPipe Face Mesh V2 states its model card places identification and life-critical decision-making outside the model's intended use — i.e., there is at least one documented use-case restriction in the model card language, separate from the code license — [Hugging Face naklitechie/face-landmarks-onnx](https://huggingface.co/naklitechie/face-landmarks-onnx)
- An unresolved, unanswered community question exists specifically about commercial use of a sibling MediaPipe bundle (Pose Landmarker Full): a Google AI developer forum thread asks whether commercial use is permitted for that model bundle, explicitly distinguishing the Apache-2.0 *code* license from the separate question of the *model bundle's* terms, with no official answer found in the thread — [Google AI Developer Forum](https://discuss.ai.google.dev/t/commercial-use-of-mediapipe-pose-landmarker-full/184033)
- MediaPipe's own Face Mesh V2 and Blendshape V2 PDF model cards were found referenced (hosted at `dcmpx.remotevs.com`/Google Cloud Storage mirrors) and reportedly state "LICENSED UNDER Apache License, Version 2.0," with the Blendshape V2 card's primary intended use described as "AR entertainment" — this was surfaced via search snippets only, not independently fetched in full — [Model Card Blendshape V2 PDF](https://dcmpx.remotevs.com/com/googleapis/storage/SL/mediapipe-assets/Model%20Card%20Blendshape%20V2.pdf); [Model Card MediaPipe Face Mesh V2 PDF](https://dcmpx.remotevs.com/com/googleapis/storage/SL/mediapipe-assets/Model%20Card%20MediaPipe%20Face%20Mesh%20V2.pdf)

### Inferences
- Treating MediaPipe's blendshape output as "driving signal compatible by name with an ARKit-style rig" is reasonable given the directly-confirmed name matches (`jawOpen`, `browDownLeft`, etc.), but an Oculus-viseme-named rig (e.g. `viseme_aa`, `viseme_PP`) would NOT be directly driven by MediaPipe's output without an explicit mapping layer, since MediaPipe's 52 names follow ARKit's convention, not Oculus's viseme convention — no evidence was found that MediaPipe outputs Oculus viseme names.
- The weight of evidence (official guide language + multiple independent third-party repackagers all agreeing) points to Apache 2.0 for both code and model weights, which would permit commercial use, but this was not confirmed from Google's own primary model-card PDF text (only from search snippets describing it) — this should be treated as "likely but not fully primary-source-verified" rather than certain, especially given the open forum question about a sibling model bundle's commercial terms going unanswered.

### Gaps
- Full, verbatim text of Google's own Blendshape V2 and Face Mesh V2 model-card PDFs was not directly fetched (only search-engine snippets were available) — the project should independently open these PDFs before finalizing any commercial-use decision.
- No official, direct answer from Google confirming commercial use of the Face Landmarker / Blendshape V2 bundle specifically was found — the closest is an unanswered community forum question about a sibling bundle (Pose Landmarker), which is a gap, not a resolution.
- The complete list of all 52 MediaPipe blendshape names (to verify 1:1 exact match against the target SDK's existing ARKit name list, e.g. confirming `mouthFunnel`, `mouthPucker`, `mouthClose`, `mouthRollLower` are all present and spelled identically) was not obtained — only 4 of 52 names were directly confirmed from the official guide.

## 4. Open Blender add-ons/pipelines for building an ARKit blendshape rig on an arbitrary head mesh

### Takeaway
Free, open-source Blender add-ons exist for generating the 52 ARKit shape keys, but every one found requires the mesh to already have a working facial rig (bones/drivers) that can be posed into the 52 reference expressions by hand — none of them auto-generate ARKit blendshapes on a truly unrigged, arbitrary scanned head without that manual rigging and posing step first.

### Cited Findings
- `elijah-atkins/ARKitBlendshapeHelper` — a Blender addon described as generating "ARKit blendshapes for facial motion capture." Confirmed via direct fetch: it requires a resting Basis pose on frame 0 and the 52 ARKit poses hand-posed on frames 1-52 of an *already-rigged* character, using a source object and a duplicate target object chosen in the panel; outputs blendshapes baked onto the target head. The page shows the 52 ARKit names in pose order and the panel displays the expected pose name per frame, strongly suggesting (but not explicitly confirming) that output shape keys get ARKit names automatically. No LICENSE file/terms found in the fetched content — only attribution crediting a YouTube tutorial by TheRoyalSkies. Maintenance: 43 commits, 96 stars, one v1.0.0 release, but no confirmed last-commit date — [GitHub](https://github.com/elijah-atkins/ARKitBlendshapeHelper)
- `tsikerdekis/ARKit-Creator-Blender-Addon` ("ARKit Blendshape Baker") — confirmed via direct fetch: MIT License. Requires Blender 4.4.x+ and an already-rigged face (built with Rigify or AutoRig Pro); walks the user through each of the 52 ARKit shapes with reference images while they pose and bake each one by hand; outputs shape keys plus an automatically-created Basis, with an FBX export step at the end (recommends AutoRig Pro's "ARP Export FBX" to preserve bone naming). The page says shapes are "ARKit-compatible" but does not explicitly confirm the exported shape-key names match ARKit's standard strings exactly — this should be spot-checked in Blender's Shape Keys panel after running it. Maintenance: only 3 commits shown, no confirmed date — [GitHub](https://github.com/tsikerdekis/ARKit-Creator-Blender-Addon)
- `ysk424/niramekko` — MIT-licensed, but solves a different problem: it receives *live* iPhone ARKit facial-capture data (via the Face Cap app over OSC/UDP) and drives an *existing* character's shape keys in real time; it does not generate new blendshapes on an unrigged mesh — [GitHub releases](https://github.com/ysk424/niramekko/releases)
- Paid/non-open alternatives were explicitly found and excluded per task constraints: "YAARKitHelper" and "ShapeKeyGen" (Superhive/Booth marketplace, one-click 52-shape generation) and "ARKit Magic" ($9.99, Superhive) — these are commercial Blender Market-style assets, not open source, and are listed here only to confirm they were considered and excluded, not recommended — [YAARKitHelper (Booth)](https://booth.pm/en/items/8433374); [ShapeKeyGen (Superhive)](https://superhivemarket.com/products/shapekeygen); [ARKit Magic (Superhive)](https://superhivemarket.com/products/arkit-magic)

### Inferences
- Both open-source Blender tools found (`ARKitBlendshapeHelper`, `ARKit-Creator-Blender-Addon`) assume a pre-existing bone-driven facial rig capable of being posed into all 52 ARKit expressions — this means they are rig-to-blendshape *bakers*, not mesh-to-rig *generators*. For a raw scanned/reconstructed head mesh with no rig at all, these tools are not directly usable; the realistic combined workflow is: rig a single template head once (manually, with bones, correctives, or sculpted shape keys) → use one of these addons to bake its 52 ARKit shape keys cleanly and with correct naming → then use deformation transfer / non-rigid ICP (Section 2) to carry that already-named 52-shape set onto each new unrigged scan. This makes the Blender addon step a one-time, per-template manual effort, while the deformation-transfer step is the per-avatar automatable part.
- Given neither tool's page explicitly guarantees exact-string ARKit naming in its output, a manual verification/renaming pass (checking each shape key name against the SDK's expected list: `jawOpen`, `mouthFunnel`, `mouthPucker`, `mouthClose`, `mouthRollLower`, etc.) should be budgeted as a required QA step regardless of which addon is used.

### Gaps
- Neither Blender addon's documentation explicitly confirms the literal output shape-key name strings match ARKit's standard camelCase convention exactly (e.g., confirmed as `mouthFunnel` vs. some variant spelling) — this needs hands-on verification in Blender, which is outside the scope of a documentation-only research pass.
- `ARKitBlendshapeHelper`'s exact license terms are undocumented in the repo page content fetched; this is a real gap for any commercial-use decision and should be resolved by checking the repo's root directory for a LICENSE file directly, or contacting the author, before shipping a commercial product built on it.
- No open-source tool was found that builds the 52 ARKit shapes on an arbitrary mesh via shrinkwrap/corrective-smooth from a template *without* also requiring a pre-existing bone rig to pose through — i.e., a pure "shrinkwrap the template's shape-key deltas onto the new mesh" script (as distinct from deformation transfer with explicit correspondence) was not found as a dedicated open-source project; it would likely need to be hand-written using Blender's Shrinkwrap + Corrective Smooth modifiers, which is a standard but manual/undocumented-as-a-package technique.

## 5. glTF/GLB export tooling for getting a Blender blendshape rig into GLB with correctly named morph targets

### Takeaway
Blender's own glTF exporter carries shape-key names through to the exported file as an array in `mesh.extras.targetNames`, order-matched to each morph target's index — this is the mechanism a Three.js renderer would need to read in order to look up morph targets "by name," but it is a Blender-exporter convention living in `extras`, not a field defined by the core glTF 2.0 specification itself, so correctness depends entirely on exact Blender shape-key naming and on the loader (e.g. Three.js's GLTFLoader) actually reading `extras.targetNames`.

### Cited Findings
- A Vulkan/glTF tooling tutorial states that Blender shape keys should be given semantic names (examples given: `blink_l`, `smile`, `mouth_open`) and that "these names are exported in the glTF `extras.targetNames` field," allowing an engine to address morph targets by name rather than only by index — this is a secondary/tutorial source, not the Khronos spec itself, so the exact field path should be verified against the current Blender exporter's output on a real export — [Vulkan Tutorial — Blender-to-Vulkan Workflow](https://docs.vulkan.org/tutorial/latest/Advanced_glTF/Tooling_Production_Pipeline/02_blender_workflow.html)
- A Three.js discourse thread on "Animation and Morph Target GLTF Export" confirms a related, separate pitfall: the Blender exporter does **not** include *muted* shape keys in the export at all — if a shape key's mute flag is enabled in Blender, it is silently dropped from the GLB rather than exported as a zero-weight target — [Three.js Discourse](https://discourse.threejs.org/t/animation-and-morph-target-gltf-export/14850)
- A Khronos Community forum thread ("Blender Shape Keys and Sparse Accessors") reports that Blender's exporter stores each shape key as a full dense accessor (not a sparse accessor), meaning the exported morph-target buffers contain explicit zero values for every vertex the shape key doesn't affect, rather than a compact sparse representation — this is a file-size/efficiency note, not a naming issue, but relevant for GLB size budgeting with many (50+) morph targets — [Khronos Community Forum](https://community.khronos.org/t/blender-shape-keys-and-sparse-accessors/108440)
- A Blender Artists forum thread warns that if a head mesh has multiple materials, Blender's glTF export splits it into multiple mesh *primitives*, and some viewers then show a separate morph-target slider set *per primitive* — meaning a single named shape key can visually appear to be duplicated/split across primitives in certain glTF viewers, which is a practical pitfall for a renderer that expects one flat list of named morph targets per mesh — [Blender Artists thread](https://blenderartists.org/t/when-exporting-gltf-from-blender-multiple-meshes-appear-in-the-morph-target-in-the-viewer/1523555)
- Shape-key *animation* (as opposed to the static morph-target basis) is only exported where there are actual keyframes driving the shape-key values in Blender, and requires the relevant shape-key export options to be enabled in the glTF export dialog — found via search snippet, not independently verified against the current exporter UI — [Three.js Discourse (same thread)](https://discourse.threejs.org/t/animation-and-morph-target-gltf-export/14850/10)

### Inferences
- For a Three.js renderer that reads morph targets "by name" from a GLB `SkinnedMesh`, the practical requirement is: (a) name every Blender shape key with the exact target string (e.g. `jawOpen`, `mouthFunnel`) before export, (b) ensure none of the 52 shape keys are muted at export time, (c) keep the head mesh as a single material/single primitive if the downstream viewer or Three.js loading code assumes one flat morph-target list per mesh (to avoid the multi-primitive splitting pitfall), and (d) confirm in code that the loader reads `mesh.extras.targetNames` (or whatever equivalent array Three.js's GLTFLoader populates, e.g. `mesh.morphTargetDictionary`) rather than assuming name-to-index mapping is automatic — this is a one-time per-template export-pipeline setup, but should be scripted/checked per-export since muting or material-splitting mistakes are easy to reintroduce.

### Gaps
- The exact current (2026) Blender glTF exporter behavior was not independently verified against Blender's own official I/O glTF 2.0 add-on documentation or source code — all findings here come from third-party tutorials and forum threads, which the researcher.md guidance flags as secondary sources; the project should do a quick hands-on test (export a simple multi-shape-key mesh from the actual Blender version in use, inspect the resulting `.gltf` JSON's `extras.targetNames` array) to confirm this is still accurate.
- Whether Three.js's `GLTFLoader` reads `extras.targetNames` into `mesh.morphTargetDictionary` automatically (which is the detail that actually matters for "reads morph targets by name") was not directly confirmed from Three.js's own documentation or source in this research pass — this is an important remaining gap since it is the exact mechanism the existing SDK's renderer presumably depends on.
- No official Khronos glTF 2.0 specification page was directly fetched to confirm whether `KHR_materials_variants`-style or any newer official extension (as opposed to the informal `extras.targetNames` convention) now exists for naming morph targets — this should be checked against the current glTF 2.0 spec repository directly if precision on this point matters.
